## How to look

**1. Choose the slice by judgment.** Name at most five test classes, or a
short list of specific methods within them. Prefer tests that already look
suspect: ones with sleeps, timeouts, wall-clock assertions, tolerance windows,
iteration over an unordered collection, or a dependence on seeding or GPU
state.

**2. Run the SAME named selection repeatedly.** Use the MCP test runner and
name the exact classes or methods — never a module, a whole suite, a Surefire
wildcard, or a CI shard selector (that is CI-shard partitioning, not yours to
use):

    mcp__ar-test-runner__start_test_run module:"<module>" test_classes:["FooTest","BarTest"]
    mcp__ar-test-runner__start_test_run module:"<module>" test_methods:["FooTest#a","FooTest#b"]

Give every run an explicit timeout of at most 2400 seconds. Repeat the SAME
small selection several times (begin with five to ten runs) rather than
widening it: a test that is flaky one run in ten shows itself by repetition of
a narrow selection, not by running more tests once. If a slice looks stable
after a reasonable number of repeats, say so and either pick a different small
slice within the module or report the slice clean — do not widen a single run
to cover the module.

**Do not try to force a flake by oversubscribing the host.** Running many heavy
selections at once, or piling on parallelism to "stress" the machine into
failing, does not reproduce a real flake — it exhausts memory and gets the
session killed (a previous round was killed with exit 137 doing exactly this).
Reproduce by repeating a narrow selection on the quiet host, not by overloading
it.

**3. Confirm the flakiness before believing it.** One failure in ten runs is a
finding only once you can point at the run that failed and the run that passed
on the same commit. Record the exact outcomes you saw. A test that fails for a
real, deterministic reason on this commit is a different finding — a broken
test, worth reporting — not a flaky one. For a flake you take from the observed
list but cannot run here, the disagreeing CI attempts are already that evidence.

## When you find (or confirm) a flaky test

Diagnose the source of the nondeterminism and decide where it lives:

- **Production or test-helper code (fix it here).** When the varying outcome
  comes from the code under test or from a shared test fixture, helper, or
  base class — an unseeded random source, iteration over a `HashMap`, a
  resource not reset between tests, a race in the production code — fix it
  there. A deterministic fix (seed the generator, order the collection, reset
  the shared state, close the race) is the best outcome. Prove it by running
  the same named selection again, repeatedly, and showing the outcome is now
  stable.

- **You must NOT edit the existing test methods.** The test that revealed the
  flakiness is the specification, and this round runs with the test lock on.
  Do not delete it, weaken an assertion, widen a tolerance, raise `@TestDepth`,
  inflate a timeout, shrink a dimension, or add a skip/`Assume` guard to make
  it stop varying — those hide the defect instead of fixing it, and
  `test-integrity-check` rejects them. Adding a NEW test, or editing a shared
  fixture/helper that is not itself an existing test method, is allowed when it
  is what the fix needs.

- **Otherwise, file a follow-up carrying the evidence and your diagnosis.** When
  the cause is outside this pilot's narrow scope, needs a larger refactor, runs
  on a lane you cannot reproduce here, or you cannot pin it down with confidence,
  file a backlog task with `tracker_create_task` (give it the project id, a clear
  title, and a description naming the module, the test, the exact attempts or
  runs that disagreed, the lane, the recorded failure output, and what you
  believe the cause is). Report its id in your summary rather than editing code
  you are unsure about. This is the same follow-up routing the general review
  uses. A diagnosed flake with its evidence filed is a complete round; a bare
  "could not reproduce" is not.

## What counts as success

In descending order:

1. A demonstrated flaky test, a diagnosed cause, and a deterministic fix in
   production or test-helper code, proven by repeated runs now stable.
2. A demonstrated or CI-confirmed flaky test, honestly reported, with a
   follow-up task filed that carries the evidence (the disagreeing attempts, the
   lane, the recorded failure output) and your diagnosis — because the fix is out
   of this pilot's scope or the lane is not reproducible on this host.
3. A careful account of the leads you examined, how many times you ran each, and
   the outcomes you saw, concluding that the slices you could run are stable on
   this commit. An honestly empty-handed round is a valid outcome; do not
   manufacture a finding, and do not widen the run to chase one. But do not
   mistake a lane you could not run for a clean slice — diagnose it from its
   recorded output or file it with that evidence.

## Constraints

- Named, bounded test selections only, each with an explicit timeout of at
  most 2400 seconds. Never a module's whole suite, a wildcard, or a CI shard
  selector. Repeat a small selection; do not widen it, and do not oversubscribe
  the host to force a failure.
- Do not edit, weaken, disable, or skip any existing test method.
- Do not report a flaky test you have not reproduced or confirmed from CI's
  recorded attempts, and report the actual outcomes, not a claim that you
  verified it.
- Keep the change focused on the one source of nondeterminism you found. If
  you find several, fix or file the most serious and note the others in your
  summary.
