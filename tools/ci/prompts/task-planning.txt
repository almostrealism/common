## Step 2: Understand the task

Read the task's title and description closely. Then investigate what the task
touches: use `consult` (`mcp__ar-manager__consult`) for the components
involved, read the relevant code and documentation, and check `docs/plans/`
for plans that already cover part of the work. If the task
names tasks it is blocked by, they have closed; find what they delivered, since
this task builds on it.

## Step 3: Write the plan

Create exactly one new plan document: `docs/plans/PLAN-<YYYYMMDD>-<short-slug>.md`.
It must start with the lifecycle front matter described in `docs/plans/CLAUDE.md`,
with `status: proposed`, today's date as `created`, an empty `closed`, and the
tracker task's id in `tracker`:

    ---
    status: proposed
    created: <YYYY-MM-DD>
    closed:
    tracker: [<task id>]
    ---

After the front matter it should contain:

- **Title**, and the tracker task it plans: its id and title, and the release.
- **Motivation**: why the task matters, in the task's own terms.
- **Scope**: concretely, what will change. Stay within the task. If doing the
  task properly needs work outside it, name that work as a dependency or an
  open question instead of widening the scope.
- **Approach**: how the work will be done, grounded in the code as it is: the
  classes, modules and files involved, and where new behaviour belongs.
- **Success criteria**: how a reviewer will know the task is done, including
  the tests that will prove it.
- **Dependencies** and **open questions**: anything the person approving the
  plan needs to decide or know first. If the task looks too large for one
  change, say so here and propose how to split it.
- **Estimated complexity**: small, medium or large.

Do not edit `docs/plans/MANAGER_LOG.md`: it records the free-form planning
round's reasoning, not tracked work. Do not change code, tests or any file other
than the new plan document and, when the work needs it, the settings file below.
