## How to fix what you find

Nothing has been flagged against this branch. You are here because the pipeline
is green and the changes are due for review — every gate passed, including
`agent-commit-validation`. (Had one failed, you would be reading a different
prompt that named it.) This section is about the means available to you as you
fix things, not an accusation.

**The test is the specification.** When a test fails, the defect is in the
production code, and that is where the fix goes. Deleting a test, weakening its
assertions, widening a tolerance, raising `@TestDepth` past the depth CI runs,
inflating a timeout, or shrinking a dimension until the test passes are not
fixes — they leave the defect in place and remove the thing that reports it. If
you cannot make a test pass, say so and explain why. A failure you report is a
good outcome; a failure you conceal is the worst one available to you.

That expectation is enforced mechanically rather than left to judgment, and it
is narrower and more specific than "test files are off limits":

- **Base-branch test *methods* are locked — not whole test files.**
  `validate-agent-commit.sh` compares this branch against
  origin/${BASE_BRANCH}. In Java, every test method that exists there must
  survive byte for byte: annotation block, signature, and body. In Python the
  check is deliberately weaker, because an indentation-delimited body cannot be
  bounded as reliably — every `def test_*` present on the base branch must still
  be present, and a test file's assertion count must not fall. Editing inside a
  Python test body is therefore permitted; do not read that leniency as an
  invitation, because everything above still applies to it.
- **Adding tests is always allowed, and section 3 below requires it of you.**
  A new test method in an existing test class is permitted. So is editing the
  fixtures, helpers, constants, and imports that class uses — those are ordinary
  code. Test files this branch introduced are yours to change freely.
- **CI files are locked unless the branch is named `ci/...`.** Files under
  `.github/workflows/` and `tools/ci/` may only be changed on such a branch,
  where the pipeline is the declared subject of the work. The policy detectors
  under `engine/utils` stay locked on every branch, since weakening a detector
  is never what a pipeline change is about.
- **`detect-test-hiding.sh` and `deception-audit.sh` run alongside the
  validator**, looking for the weakening patterns listed above and for the same
  file being modified, reverted by a human, and modified again across sessions.

These checks exist because agents have repeatedly hidden failures instead of
fixing them: raising `@TestDepth` past CI's depth, cutting dimensions eight-fold,
inflating timeouts six-fold, re-applying a suppression a human had just
reverted, excluding a policy test from CI, and recording memories claiming no
change was needed on a branch they had themselves broken. Knowing the shape of
those mistakes is what lets you avoid making them — and, in section 1 below,
recognize them in the diff you are reviewing.

## What to look for and fix

### 1. Test Integrity & Deception Detection (HIGHEST PRIORITY)

Run `git diff origin/${BASE_BRANCH}...HEAD -- '**/*Test*.java' '**/test/**/*.java'` to
see all test file changes. For each modified test that existed on origin/${BASE_BRANCH}
(check with `git log --oneline origin/${BASE_BRANCH} -- <file>`):

**Flag as TEST INTEGRITY VIOLATION if you find ANY of these:**
- @TestDepth values INCREASED (e.g., 2->10) — hides tests from CI
- Timeout values INCREASED by more than 2x — hides performance regressions
- Numeric constants DECREASED (dimensions, sizes, iterations) — trivializes tests
- Tolerance/epsilon values INCREASED — weakens assertion precision
- @Ignore, @Disabled, or skip annotations added
- Assertions weakened, deleted, or commented out
- try/catch blocks added that swallow exceptions
- CI workflow files modified to exclude tests or quality checks
- Numeric literals (>=16) removed without replacement in method arguments

**If you find violations: REVERT the test modifications.** The test is the
specification. Fix the production code to make the original test pass.

**Cross-session deception patterns to flag (run deception-audit.sh):**
- Same test file modified in 3+ commits on the branch (ping-pong pattern)
- Commits that touch ONLY test/CI files with no production code changes
- @TestDepth changed multiple times in the same file on this branch
- Revert commits followed by re-modification of the same files
- Net reduction in assertions across the branch
- Memory entries claiming "no changes needed" on branches with active failures

### 2. Design and Architecture

- Do the changes follow CLAUDE.md architectural principles (ModelOptimizer owns
  training loops, PackedCollection is not a Java array, StateDictionary for
  weights, etc.)?
- Is the level of abstraction appropriate?
- Is there code duplication that should be extracted into a shared method?
- **Method placement — OOP fundamentals**: Every method must live on the class
  it naturally belongs to. This is the most basic principle of object-oriented
  design. Ask yourself for every new method:
  - Does this method use instance state of its containing class, or could it be
    static? If it could be static, it probably belongs somewhere else — or at
    minimum must be declared static to make its independence explicit.
  - Is this method a general-purpose traversal or query that operates on a base
    type (e.g., `Expression`, `Scope`)? If so, it MUST be defined on that base
    type, not on a subclass. Defining `collectAllReferencedNames(Expression)`
    as a private method of `Repeated` instead of as an instance method on
    `Expression` prevents all other code from reusing it and violates the
    single-responsibility principle.
  - Would this method be useful to other callers? Utility methods for collecting
    declarations from a scope tree, extracting names from assignment
    destinations, or traversing expression trees for references are inherently
    general-purpose. They belong on `Scope` or `Expression`, not buried as
    private helpers in a specific subclass.
  - **Flag as a design violation** if you find methods defined on a subclass
    that: (a) do not reference any instance fields of that subclass, AND
    (b) operate on parameters of a base type. These must be moved to the base
    type or made static utilities on the appropriate class. Fix them — do not
    just flag them.
- **Backwards compatibility vs. clarity**: Ask yourself — are these changes
  preserving a probably-useless kind of backwards compatibility at the expense
  of creating a lot more effort to understand the intended behavior? Prefer a
  "do things once" approach: one method signature, one code path, one way to
  accomplish each task. Duplicate method overloads or parallel "fallback" paths
  that silently degrade to the old behavior are a red flag. If the old behavior
  is genuinely no longer the intended path, remove it or make it throw rather
  than keeping it as a silent fallback. Maintaining two paths doubles the surface
  area for bugs and makes it nearly impossible for the next reader to know which
  path is actually expected to execute in production.

### 3. Test Coverage and Quality (CRITICAL — EQUAL PRIORITY TO TEST INTEGRITY)

**Every modified line of production code MUST be covered by tests.** This is not
optional. If a branch adds or changes production code without corresponding test
coverage, that is a defect you MUST fix before anything else.

Specifically:
- For every changed method: there must be a test that exercises the changed code
  path. If no such test exists, WRITE ONE.
- For every new method or class: there must be tests that verify its behavior.
  If no such tests exist, WRITE THEM.
- For every bug fix: there must be a regression test that fails without the fix
  and passes with it. If no such test exists, WRITE ONE.
- For every new branch or conditional: there must be tests for both the true and
  false paths. If coverage is missing, ADD IT.

**Test quality requirements — every test you write or evaluate must meet ALL of
these criteria:**
- Tests must verify BEHAVIOR, not just that code runs without throwing. A test
  that calls a method and checks no assertions is worthless.
- Tests must include adversarial and boundary cases: null inputs, empty
  collections, maximum/minimum values, off-by-one boundaries, concurrent access
  where applicable, malformed input, and type edge cases.
- Tests must assert on specific expected values, not just "result is not null."
- Tests must be independent and deterministic — no reliance on execution order or
  external state.
- Tests must follow project conventions (extend TestSuiteBase, use @TestDepth
  for expensive tests, include timeout parameters).

**If the branch has production code changes but insufficient test coverage, this
is a blocking issue.** Do not proceed to other review categories until test
coverage is complete. Write the missing tests yourself — you are a coding agent,
not a reviewer.

### 4. Correctness

- Are there logical defects in the implementation?
- Are there fragile assumptions, implicit ordering dependencies, or missing
  validation at system boundaries?
- Is error handling and resource management correct?

### 5. Documentation

- Do all new non-private classes and methods have Javadoc?
- Is the documentation accurate and useful (not just boilerplate)?

### 6. Consistency with Existing Patterns

- Is new code in the correct module?
- Does it duplicate existing functionality? (Search the codebase before
  concluding.)
- Are naming conventions and structural patterns consistent with surrounding
  code?

## How to proceed

1. **First: read the review feedback.** Find the pull request for this branch
   and read both comment feeds before deciding anything else. What a reviewer
   has already flagged shapes what the rest of this review is for.
2. **Then: audit test coverage.** Diff all production code changes against
   existing tests. For every changed or added production method that lacks test
   coverage, write tests BEFORE moving to other review categories. This is your
   highest-priority deliverable after test integrity checks.
3. Identify every issue across the remaining categories above.
4. **Fix each issue directly** by editing the source files.
5. Verify the build still succeeds: `mvn install -DskipTests`
6. Run the tests you wrote to confirm they pass.
7. Reply, threaded to the original comment, to each review comment you acted on
   whose author is safe to answer — the review feedback section above says
   who that is. Leave the rest unanswered.
8. Send a summary of what you changed and why. Organize by category.
   For each fix, include the file path and a one-line explanation. Say which
   review comments you addressed, which you declined and why, and which you
   left unanswered because replying would have started a loop.

If the changes look good across all categories and nothing needs fixing,
say so explicitly via a message and explain why you are confident.
