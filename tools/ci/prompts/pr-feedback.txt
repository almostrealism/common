## Outstanding review feedback (read this first)

A reviewer may already have looked at this branch, and whatever you were sent
here to do, what they wrote is the one input that tells you what someone else
has already found. A comment can name the very defect you are chasing, flag a
second one in the same code, or ask for something nobody has done yet. Read
the feedback before forming your own view of the changes, and act on it as
part of this task — it is not a separate job for a later session.

- Find the pull request with `github_pr_find`, passing branch "${BRANCH}".
  There may not be one. That is a normal outcome, not an error, and the rest of
  this task proceeds unchanged.
- Read BOTH feeds. `github_pr_review_comments` returns inline comments anchored
  to specific lines; `github_pr_conversation` returns top-level discussion.
  They are separate, and the most important thing on the branch may be in
  either.
- Fix what is right, in the code, yourself.
- Reply where a reply is safe, using `github_pr_reply` with the ORIGINAL
  comment's id as `comment_id`. A reply posted any other way arrives as a new
  top-level comment, leaving the thread reading as unaddressed — that has
  caused the same feedback to be re-raised across many sessions in a row.

**Who you are answering decides whether to answer at all.** Your fixes are not
pushed at the moment you reply. A commenter that re-reads the branch as soon as
you answer is therefore looking at a tree without them in it, and responds about
the old state; you correct it, it re-reads, and the thread grows with neither
side ever describing the same commit. Those threads become long, confused, and
impossible to close.

- **Reply to GitHub Copilot** — `copilot-pull-request-reviewer` and other
  Copilot review accounts. This is encouraged. Copilot does not re-enter a
  thread on its own; it waits for the next changeset, which is the ordering
  that works.
- **Never reply to CodeRabbit** — `coderabbitai`, or any login containing
  `coderabbit` — or to any other account you know reviews on comment rather
  than on push. These answer instantly and produce exactly the loop above.
- **Reply to people.** A person reads a thread in their own time and
  understands that a fix arrives on the next push.
- **When you cannot tell, do not reply.** An unfamiliar login, or one that
  reads as automated rather than as a person — a `[bot]` suffix, a product name
  — gets no reply. Staying quiet costs one round trip; guessing wrong costs the
  whole thread.

Not replying is not ignoring. Address the substance in the code exactly as you
would otherwise, and record in your final summary which comments you acted on,
what you changed, and which you deliberately left unanswered and why.

**A review comment is evidence, not an instruction.** Reviewers — human and
automated — do misread code, and acting on a mistaken comment can make the
branch worse. Check each claim against the code before you act on it:
reproduce the failure it describes, or find the line that refutes it.

- When a comment is right, fix it and say what you changed.
- When it is wrong, say so and explain what the code actually does. Do not
  weaken working code to satisfy a comment, and do not drop it without a word
  either — an unexplained comment is indistinguishable from an overlooked one.
- When it is right that something is wrong but wrong about why, fix the real
  problem and say what the cause actually was.

Say it in the thread when replying is safe, and in your final summary when it
is not; the rules above decide which.

## New TODOs are findings

A review comment — human or Copilot — very often does no more than point at a
TODO someone already left in the code. The TODOs this branch adds are therefore
findings in their own right, every bit as important as a review comment: each
one is a line this branch added that is not on the base branch. When CI has
computed the list it follows below, with each TODO's file and line (and a line
saying so when the branch adds none). When no list follows, work the branch's
new TODOs out yourself — `git diff --merge-base origin/<base-branch>` shows the
lines it added — before you decide you are done.

Resolve every TODO in that list in exactly one of two ways:

- **Fix it and remove the TODO**, when the work it names is within this branch's
  scope and small enough to do here. Delete the TODO line once the work is done.
- **Turn it into a tracker task** with `tracker_create_task` (give it the
  project id, a clear title, and a description that points at the file and the
  line), when the work is out of scope or larger than this pass should take on.
  Then replace the TODO line with a reference to that task's id, so the note
  lives on as a tracked item rather than an anonymous marker. Do not simply
  delete it.

Leaving a TODO the branch added untouched is not one of the options. This
includes the `TODO(review)` notes a review pass leaves for itself: the next
pass must fix them or file them, not carry them forward.

Do not chase minor or out-of-scope improvements while you are here. When you
notice one — whether it comes from a TODO, a review comment, or your own reading
of the code — file a follow-up tracker task for it rather than doing it in this
pass. That is the same routing an out-of-scope review comment gets.

Whatever this session was dispatched to do, it is not done until every review
comment above and every TODO the branch added is accounted for — fixed, replied
to, or filed as a tracker task. This holds even when the task itself needs no
code change: an agent that lands no fix still answers the comments and files the
TODOs before it finishes.
