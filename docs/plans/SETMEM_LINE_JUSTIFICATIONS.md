# setMem line justifications — PR #375 (phase 19)

One row for every line added by this branch that contains `setMem`. Each
claim was authored by a reviewer that read the full containing method (and
class context) of the site — none of the claims are generated. Where honest
reading showed a sanctioned form was possible, the code was changed instead
and the row records the replacement; REPLACED rows therefore no longer
appear in the final diff.

Recurring findings the individual claims rely on:

- `PackedCollection.fill(double...)` replaces the ENTIRE contents of the
  collection, cycling its varargs across every element. It is therefore the
  correct form for any write that replaces the whole contents — regardless
  of how many values it carries — and never a substitute for partial or
  sparse writes, where the cycling would overwrite elements the site means
  to leave alone.
- Single-arg `setMem(v)` writes element 0 only; on a size-1 buffer it and
  `fill(v)` coincide, and the replacements below use `fill` there when the
  write mutates existing captured state.
- Many keeps are tests whose subject is host-write visibility: a compiled
  kernel captured a specific collection instance, and the assertion is that
  a later host write to that same instance is observed. `pack()` allocates
  a new instance the kernel never reads, so it cannot express these.
