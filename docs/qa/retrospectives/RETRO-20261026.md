## Findings by category

### Category 1 — the FlowTree agent harness

#### F1. Copilot review has been dark the entire window, now through today (carry-forward of `copilot-review-dark`, escalated)

- **Evidence.** Every Copilot review requested on an in-window PR returns the
  identical "Copilot was unable to review this pull request because the user who
  requested the review has insufficient remaining quota." PR #727 carries **four**
  such bodies at four different commits (review ids `5633122020`, `5632871199`,
  `5632534098`, `5631138324`; 2026-10-23), and today's PR #752 carries another
  (`5646758539`; 2026-10-26T02:29Z). A defect-round memory on PR #734
  (`4595c661`) records the same: "No human/Copilot review comments (Copilot
  quota-blocked)." The prior run found the identical wall back to 2026-10-14.
- **Impact.** The pipeline is designed around two automated reviewers — Copilot
  and the agent `general-review` (`auto-review`). Copilot has posted only a quota
  notice for **≥12 consecutive days spanning two retrospective runs**, so the
  agent reviewer is the effective sole automated reviewer, and nothing in the
  pipeline flags the absent layer: a quota notice is posted as a "review," so the
  PR looks reviewed. There is a direct pipeline cost too — `auto-review-submit`
  holds `DELAY_SECONDS: "300"` on every dispatch precisely so the agent "starts
  with" Copilot's review of the same push, a five-minute wait that, all window,
  waited for a review that never came.
- **Proposal.** Primarily person-only: set the organization as the Copilot
  code-review billing source (the quota body links the exact settings page) or
  otherwise restore the quota. Separately, so the gap is visible rather than
  silent, detect a quota-limit review body and surface it (a one-line status /
  log) instead of letting a no-op stand in for a review, and stop re-requesting a
  review known to be refused; shorten or drop the `auto-review-submit` hold while
  Copilot is dark.
- **Landing.** Person-only (Copilot / org billing) for the restore; the agent-side
  request lives in `_request_copilot_review` / `github_request_copilot_review`
  in the ar-manager MCP server (an ordinary branch) if the quota-notice detection
  is added there; shortening the `auto-review-submit` hold is a `ci/qa-…` branch.

#### F2. Shared-worker `~/.m2` is not isolated between jobs, so a build can inherit a prior branch's artifacts and mask a test result (new)

- **Evidence.** Two independent in-window rounds hit the same hazard and had to
  work around it by hand. The flaky pilot's memory (`0ba88064`) ends with a
  standing note: "rebuild with `mvn clean install -DskipTests -pl engine/utils
  -am` first; `~/.m2` artifacts were stale from a prior branch." The coverage
  round's memory (`bed3c0be`) is sharper: it verified a fix "after a fresh `mvn
  install` (the `~/.m2` jars had been built from `ci/plans-cleanup`, which would
  have masked the result)." Both ran on the same macOS aarch64 worker
  (`Mac-Studio … 192.168.8.157`, from the session banners `3b1308b1` and
  `8746c615`).
- **Impact.** A round's pass/fail can depend on leftover artifacts from an
  unrelated branch's build on the same worker. An agent that knows to rebuild
  defensively gets the right answer; one that does not gets a masked result —
  a false pass or a false failure — and the retrospective and the auto-resolve
  dispatch both read that signal downstream. This is a correctness hazard for the
  entire QA signal, not just a nuisance.
- **Proposal.** Give each job a clean view of its own dependencies: a per-job
  local Maven repository, or a guaranteed rebuild of the changed modules'
  upstream artifacts from the job's own checkout before any test runs, so a
  prior branch's jars can never satisfy a dependency. The two memories show
  agents already compensating manually, which is exactly the signal that the
  isolation belongs in the harness, not in each agent's judgment.
- **Landing.** Person-only (runner-fleet / worker provisioning for a per-job
  `~/.m2`); the defensive-rebuild alternative is harness Java under `flowtree/`
  (the job's build/setup step) — an ordinary branch.

#### F6. QA workstreams registered then archived without a job — recurs, benign (carry-forward of `jobless-roundup`, third run)

- **Evidence.** Carried from the prior two runs: QA workstreams are registered by
  the cadence workflow and, when the per-round interval gate (`qa-cadence.sh`
  `MIN_INTERVAL_DAYS`) says "too recent," skipped and later swept by
  `archive-stale-workstreams.sh`, leaving a jobless workstream on record. The
  prior run disambiguated this from a dropped dispatch by finding a split *within*
  one timestamped batch (2026-10-17 05:19 ran consolidate+docs while
  defect+performance at the same minute got no job) — the signature of per-round
  intervals, not a lost batch.
- **Impact.** Benign noise: jobless workstreams the retrospective must filter each
  run. The alternative (a genuine partial-dispatch failure) cannot be ruled out
  from ar-manager data alone, which is why it stays person-only.
- **Proposal.** Unchanged, but now a **decision** rather than a restatement: the
  one-time check the prior two runs requested (read the controller dispatch log
  for one jobless 01:36-batch workstream) has no evidence of having been done.
  Either a person does it once — confirming housekeeping, after which the slug is
  retired, or finding a real dropped dispatch, which is a reliability bug — or the
  optional "register the workstream only after the cadence gate passes" cleanup is
  adopted to stop the accumulation. Three runs of restating it without a decision
  is itself the finding.
- **Landing.** Person-only (controller dispatch logs); the "register after the
  gate" cleanup is a `ci/qa-…` branch (`master-agent-dispatch.yaml` /
  `register-workstream.sh`).

### Category 2 — the existing QA jobs

#### F3. `auto-review` / `auto-resolve` re-fires per push with no per-PR convergence cap (carry-forward of `review-loop-cap`, third run → escalated)

- **Evidence.** The dispatch fires on attempt 1 of every CI run, and every commit
  is a new run, so even clean branches draw repeated no-op passes. In-window:
  coverage PR #742 drew **three** `auto-review` passes each "No quality gate
  reported a finding" (jobs `9e6e5a78`, `c1391690`, `3789f31f`) around one
  `auto-resolve` pass; PR #727 drew **four** Copilot re-requests at four commits.
  The pathological tail is unchanged from the prior runs: PR #593 reached ≈80
  jobs over ≈17.5 days. PR #704's merged `enforceChanges` cap bounds re-runs
  **inside a single job**; it does not bound the controller re-dispatching a fresh
  pass on each new CI run — the loop that produced #593.
- **Impact.** Per-round churn is low today (1–4 no-op passes), but it is
  structural and unbounded: the same mechanism that charges a clean PR a few
  passes is the one that charged ≈$799 to PR #593. This proposal has now been
  open across three retrospective runs; RETRO-20261022 explicitly deferred it to a
  `flowtree/runtime` follow-up branch that was never created, which is why it
  escalates rather than merely restates.
- **Proposal.** A per-PR remediation budget distinct from the single-job
  `enforceChanges` cap: after N consecutive passes that produce only churn without
  a quality gate flipping red→green, stop auto-dispatching and ping a person.
  `FlowTreeApiEndpoint`'s `startedAfter` de-dup and the controller-owned job-state
  tracking added in commit `5ff6e7ff5` are the natural places to count consecutive
  no-finding passes. Choosing N is a person's call.
- **Landing.** Controller Java under `flowtree/runtime` (an ordinary branch);
  passing any per-PR context the submit step needs is a `ci/qa-…` branch.

#### F4. `auto-resolve` attributes non-regression and environmental CI failures to the branch that happens to surface them (new)

- **Evidence.** Coverage PR #742's diff was only new `engine/utils` texture tests,
  yet its `auto-resolve` job (`0372bd8e`, 2026-10-25) was dispatched with "## YOU
  BROKE THESE TESTS. YOU MUST FIX THEM." for two failures the branch did not
  cause, as the agent's own memory (`bed3c0be`) records: `PatternFactoryTest#fixChoices`
  — a `KeyPosition` deserialization failure that "fails on master too
  wherever pattern-factory.json is present" (a `studio/music` concern, unrelated
  to `engine/utils`) — and `AudioSceneMultiGenomeTest#multiGenomePatternRender` —
  a 600-second timeout inside the native CUDA call `CU.memAllocManaged`,
  "unreproducible without CUDA." The agent correctly diagnosed non-ownership but
  still had to apply a `studio/music` `@JsonDeserialize` fix to get its unrelated
  coverage PR green, and could do nothing about the CUDA hang. The same
  `KeyPosition` fix was, per that memory, independently re-derived on
  `ci/plans-cleanup` and `project/task-20261023-010642`, while master was
  *simultaneously* repairing the same subsystem under a separate commit series
  (`ffe1aab52` → `c67ca2264` → `204d81566` → `c564d0c98`, 2026-10-24/25) — the
  same defect remediated several times over across parallel branches.
- **Impact.** This is the `auto-resolve` analogue of F3's churn, and arguably
  worse: it does not merely waste passes, it misdirects them. A branch is told it
  broke tests it did not touch; an agent spends a job proving non-ownership and
  then patches another module to go green; the same underlying defect is fixed
  repeatedly on parallel branches instead of once; and an environmental/hardware
  timeout is handed to an agent that structurally cannot fix it. All of that
  remediation effort is attributed to, and charged against, the wrong branch.
- **Proposal.** Gate `auto-resolve` on **regression-vs-base**: only attribute a
  failing test to the branch when that test passes on the branch's merge base and
  fails on the branch. A test that also fails on base is a master defect — route
  it to the defect round or file a `tracker_create_task`, do not charge it to
  whatever branch's CI run surfaced it. Separately, classify an environmental or
  hardware timeout (e.g. a native CUDA allocation hang) as infrastructure rather
  than an agent-fixable failure — the same spirit as the just-merged
  `harness-git-flake` DEGRADED classification.
- **Landing.** `ci/qa-…` branch for the dispatch decision and the resolve prompt
  (`analysis.yaml` `auto-resolve` wiring, `general-resolve`/resolve prompt); the
  base-vs-branch classification, if it lives controller-side, is `flowtree/runtime`
  (an ordinary branch).

### Category 3 — new kinds of QA job

The prior runs' standing Category-3 proposal — a flaky/nondeterministic-test hunt
round — **was implemented and merged this window** (PR #727), and its pilot has
run once. So this category contains no brand-new round proposal; the evidence
instead points at one refinement of the round just created.

#### F5. The flaky round picks its hunting ground blind — no evidence-directed targeting and no recall of the previous round (new, refines `flaky-test-round`)

- **Evidence.** `flaky-hunt.txt` tells the agent to "Pick ONE module (for example
  `engine/ml`, `domain/graph`, or `engine/audio`)" and to favour a module whose
  tests use sleeps, caches, GPU kernels or ordering — but it contains **no step to
  recall prior `flaky-hunt` memories** and does not point at the modules where
  determinism actually failed. The motivating evidence for the round lived in
  `feature/cuda-test-stability` (PR #625, merged DEGRADED) and
  `feature/audio-render-test-determinism` (PR #677, closed unmerged) — hardware
  and `studio`/render determinism — none of which appears in the prompt's example
  set. The pilot (`qa/flaky-20261023-203403`) ran 1,380 executions in
  `engine/utils` and correctly found nothing, and its own memory (`0ba88064`) ends
  by naming a better next target it has no way to carry forward: "studio/compose
  `BatchedRealSceneRenderTest`, whose `realGenome()` a prior note flagged as
  unseeded," or `flowtree/runtime` relay/mailbox tests.
- **Impact.** With a 7-day cadence and a fresh blind module pick each run, the
  round's coverage is a random walk rather than an evidence-directed search, and
  the pilot's own best lead evaporates between runs. The round is most likely to
  find flakiness where flakiness was already seen (cuda, render) — exactly where
  it is not being pointed.
- **Proposal.** Add two cheap steps to `flaky-hunt.txt`: recall prior `flaky-hunt`
  memories and continue from the previous round's named next-target, and bias the
  module choice toward where determinism has actually failed (hardware/cuda tests;
  `studio`/`compose` render; the relay/mailbox tests the pilot named). The memory
  mechanism already exists — the pilot wrote the memory; the prompt just has to
  read it.
- **Landing.** `ci/qa-…` branch (`tools/ci/prompts/flaky-hunt.txt`).

## Open questions for the reviewer

- **Which mechanism requests Copilot reviews (P1)?** An ar-manager tool can request
  one and a repository setting can too; the answer decides whether the "surface the
  quota notice" half is code or configuration. This run did not establish which
  mechanism issued the reviews it saw.
- **Do P2 and P3 share a counter?** Both touch the remediation loop — P3 bounds how
  many passes a PR gets, P2 fixes what a pass is dispatched for. They are
  independent but adjacent; a reviewer may want them designed together so the
  controller grows one remediation-state record, not two.
- **Is P6 worth a person's time at all?** If the dispatch log confirms the jobless
  workstreams are cadence skips, the only remaining action is the optional
  "register after the gate" cleanup, and the slug can be retired.
