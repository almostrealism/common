### Category 2 — the existing QA jobs

#### F2. The flaky round runs on a CPU-only host, but its highest-priority leads are GPU-backed — so a real, recurring flake class is structurally out of its reach (new)

- **Evidence.** `tools/ci/prompts/flaky-hunt.txt` ranks its leads GPU-first:
  after "the previous round's named next target" it lists "**hardware-backed
  tests**: GPU/CUDA kernels", then `studio/compose` rendering, with the
  CPU-reproducible concurrency tiers (`base/io` metrics, the `Node` worker queue)
  lower down. But the round executes on the same CPU-only sandbox the coding
  agents use. Two in-window rounds show the consequence directly:
  - `qa/flaky-20261108-231304` (job `5c41a040`, SUCCESS, **no PR**; memory
    `379884d2`): "native-only aarch64 docker sandbox — no GPU/Metal/CUDA/OpenCL".
    Its lead was `DifferentialAttentionAssetTest`'s gradient check, a flake whose
    tracker task describes it as failing "intermittently on every backend". The
    agent ran **130 gradient executions (FP64 and FP32), 0 failures** and
    correctly reported it as unreproducible on this host — characterizing it as a
    **GPU-backend, FP32-dominant numerical-tolerance flake** (unseeded `randnFill`
    draws feeding central finite differences at a 2% relative tolerance; GPU FP32
    reduction-ordering trips it, native FP64 agrees to ~1e-16). It diagnosed the
    fix as needing *either* GPU hardware to reproduce, *or* a framework-level
    deterministic test-seed (because the random draws are **inline in the
    base-branch `@Test` bodies**, which the per-job test lock forbids editing).
  - `qa/flaky-20261105-221739` (job `cdcbe019`, SUCCESS, **no PR**; memory
    `38efb121`): same CPU-only host; its GPU/CUDA/media leads
    (`AudioSceneMultiGenomeTest`, the CUDA `SimilarityOverheadTest`,
    `BatchedRealSceneRenderTest`) were "NOT reproducible on this host", so it fell
    through to the CPU-reproducible `flowtree/runtime` relay/mailbox tests, found
    them sound, and produced nothing.

  Across the window, **6 of 9 flaky rounds produced no PR**. The round's only two
  real wins ever — #763 (`Node` worker wake) and #787 (`MetricBase` race) — were
  both in the *CPU-reproducible* concurrency tiers, i.e. the lowest-priority
  leads, found only after the GPU leads were skipped.
- **Impact.** The flaky round spends its highest-priority effort on leads it
  cannot execute, then does useful work only on the leads it reaches last. A
  genuine, recurring class of real flakes — GPU-FP32 numerical-tolerance failures
  in the gradient/asset tests — is **permanently unreachable** by the round as
  dispatched: the round honestly reports "could not reproduce" every time, the
  underlying flake stays open, and no amount of lead-list tuning changes that,
  because the constraint is the host, not the targeting. This is distinct from
  the prior `flaky-target-memory`/`flaky-infra-concurrency` proposals, which were
  about *where* to point the round; this is about *what the host can run*.
- **Proposal.** Close the reach gap by one of two independent routes, for a
  person to choose:
  - **(a) A framework-level deterministic test-seed (recommended; higher
    leverage, no hardware cost).** Add a global seed the collection/test random
    helpers (`randnFill` and the `random()` test helper) honor via a system
    property or environment variable. A seed makes the random *inputs*
    deterministic and replayable across hosts — it does **not** make a
    GPU-specific FP32 reduction-ordering failure appear on the CPU-only/FP64
    host, which still agrees to ~1e-16 and passes. What it buys is the two
    things the round cannot do today: (i) on a GPU host it turns a
    "sometimes-fails-on-GPU" outcome into a *deterministic* one, so the failing
    draw is fixed and the real cause (finite-difference step vs. tolerance, or a
    genuine gradient bug) can be isolated and fixed — this is the prompt's own
    stated goal ("a deterministic fix … seed the generator"); and (ii) even on a
    CPU-only host it lets a run pin the exact draw, which separates a true
    finite-difference/tolerance bug (a seeded CPU run can surface this) from a
    pure GPU-ordering effect (which still needs route (b) to observe at all).
    This seeds for **reproducibility, not to make a flaky test pass**, and it
    sidesteps the test-lock blocker the agent hit (the draws are inline in
    base-branch `@Test` bodies) because the seed is framework-level, not
    per-test. It benefits the whole suite's input-reproducibility, not only the
    flaky round.
  - **(b) Give the flaky round a GPU-capable runner (person-only; fleet).** Route
    a flaky round whose chosen lead is a GPU-backed test to a runner with
    CUDA/Metal, so those leads are reproducible at all. This is the only way to
    reproduce a flake that is genuinely GPU-ordering-specific rather than
    seed-specific.
- **Landing.** (a) an ordinary branch — the random source is
  `PackedCollection.randnFill` in `compute/algebra`, so the seed hook belongs on
  the `randn`/`randnFill` path there; the shared test harness that would expose
  and default it (`TestFeatures`/`TestSuiteBase`) is in `engine/utils`, and the
  per-test `random(...)` wrappers that call `randnFill` live in the affected test
  modules (e.g. `engine/ml`). (b) person-only — the runner fleet
  and the round's label routing. Note: the prompt itself already handles the gap
  gracefully ("Say so and move to the next lead. Do not report it as clean"), so
  **no prompt change is proposed** — the fix is capability, not wording.

### Category 3 — new kinds of QA job

#### F3. No new *kind* of round is warranted; the one scope decision to make is backward coverage of reusable rounds run on other repos, which is `retro-cross-repo-scope` escalated

- **Evidence.** The three inputs that would justify a new round all point the
  other way, as in the prior window. (1) **Failures do not concentrate**: ≈4 of
  73 QA rounds failed operationally (one stall-FAILED `qa/defect-20261105-051447`;
  two lost SUBMITTED dispatches; one jobless cadence-skip) — all operational
  rather than a code-defect class, and the lost dispatches are already covered by
  #846's escalate-only recovery; non-QA failures are likewise isolated. (2) **The one recurring
  reactive-bug class is already covered**: shared-state concurrency, which is
  exactly what the flaky round now targets (`base/io` metrics and the `Node`
  worker queue were added to its leads by #840). (3) **Effort concentrates in the
  owner-driven remediation/dispatch infrastructure** (#832 → #840/#841/#845/#846/
  #854/#859/#860/#868 → open #883), which is converging, not expanding. A new
  autonomous round editing the controller or `ci/` scripts would run straight
  into the CI-file lock and the review-cycle cost that subsystem is bounding.
- **The real Category-3 item is a scope decision, not a new round.** The reusable
  `qa-round.yaml` (#785) and the application-caller readiness of #833 mean QA
  rounds can now run on *other* repositories, whose outcomes — did the PR merge,
  how many remediation cycles, where an agent looped — are **invisible** to the
  retrospective, the only backward-looking check, which is pinned to this repo by
  design and for privacy (a job token can reach private downstream repos; this
  report may read none of them). This is `retro-cross-repo-scope`, open for a
  second run. No application round's history is visible in this repo-scoped
  survey — but that is not proof none has run, because the reusable workflow
  registers each caller's workstream under the *caller's* `REPO_URL`, so an
  application round would not appear among the 578 all-`common` branches counted
  here.
- **Impact.** Proposing a brand-new round would add cadence and review load for no
  evidenced gain. The one genuine forward risk is the cross-repo blind spot, and
  it is a scope/policy decision (where a per-repo, privacy-scoped QA summary is
  written and who reads it), not a new round.
- **Proposal.** Decide the cross-repo policy **before** application-repo rounds
  accumulate history: either give each consuming repository its own retrospective
  that writes into that repository, or have the shared infrastructure emit a
  per-repo, privacy-scoped QA summary a person reads. (Carried as P2 below.)
- **Landing.** person-only for the policy; `ci/qa-…` for the small change to
  `tools/ci/prompts/retrospective.txt` or `qa-round.yaml` that records it.
