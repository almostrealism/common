#### F2. A primary job stalled for 12 hours and outlived its own PR's merge; a terminal PR event does not cancel in-flight jobs on the branch (new)

- **Evidence.** `project/task-20261031-170732` job `c1cae26e` (description
  "Implement the plan") was dispatched **2026-11-01T16:12** on the shared macOS
  worker and killed only at **2026-11-02T04:16** with `Job stalled: no heartbeat
  for 720 minutes`. That branch's PR **#800 merged at 2026-11-01T17:40** — so a
  primary implementation job ran, stalled, and held a scarce GPU worker for
  ≈10.5 hours *after* the work it was implementing had already been reviewed and
  merged. The stall watchdog did fire (correctly), but only after the full
  12-hour silence window.
- **Impact.** Two costs compound: the no-heartbeat threshold is long enough that
  a single hung agent occupies a worker for half a day before reclamation, and
  nothing ties a branch's terminal PR state (merged/closed) to the jobs still
  running on it — so a job keeps burning a worker on work that is already done.
  This is isolated (one instance in the window), but the fix is small and
  low-risk, and it composes with plumbing PR #832 is already adding.
- **Proposal.** (a) When a branch's PR reaches a terminal state (merged or
  closed), cancel any in-flight job still running on that branch. PR #832 adds a
  `JobLifecycleRecorder` that already observes terminal **job** events at the
  controller; extending the controller to react to terminal **PR** events is the
  natural companion. (b) Emit a no-heartbeat *warning* partway through the
  silence window (and consider a shorter reclaim once the branch's PR is closed),
  so a stall is visible well before the 12-hour kill.
- **Current state.** Still open after #832 merged. `JobLifecycleRecorder` is on
  master, but `StuckJobScanner` still has only the single kill at the threshold,
  and no code path reacts to a terminal PR event by cancelling jobs.
- **Landing.** Harness Java under `flowtree/runtime` (controller job lifecycle /
  dispatch), an ordinary branch.

#### F7. Agents keep baking ephemeral identifiers into permanent assets; the rule against it is documented but not mechanically enforced (new)

- **Evidence.** This window carries a concrete instance, inside a PR that was
  itself in flight at the survey snapshot. PR #831 (`ci/qa-round-hygiene`, open
  at the survey snapshot 2026-11-04T05:02:42Z — hence "in progress" in the status
  table above — and merged later the same day, at 2026-11-04T18:12Z) landed a
  flaky-round retargeting
  (`flaky-target-memory`) whose first draft of `tools/ci/prompts/flaky-hunt.txt`
  **hardcoded four ephemeral tracker task ids** (`fcaf8950`, `96f03d35`,
  `ad2da648`, `0891319b`) as the round's target lanes, and
  `tools/tests/test_prompt_builders.py` **asserted on those same ids**. Commit
  `a52771d56` ("Drop ephemeral tracker ids from the flaky-hunt prompt") replaced
  them with durable test-class/module descriptors plus a run-time
  `tracker_search_tasks` lookup, and the same change added the "No temporary
  identifiers in permanent assets" CODE QUALITY rule to `CLAUDE.md`. The defect
  was caught **only** by the owner's PR review comment ("NO TEMPORARY
  IDENTIFIERS"), not by any automated check — the branch had already compiled,
  passed its tests, and would have merged with the ids baked in. This is the same
  failure mode the retrospective itself must guard against: a permanent asset
  (a CI prompt, a test assertion, source, javadoc, a doc) pinned to a tracker
  task id, a job/run/workstream id, a short git SHA, a memory id, or a round's
  timestamped branch name — each of which is superseded or archived, after which
  the identifier is a dead reference that misleads the next reader and a test
  that asserts on one breaks for no real reason.
- **Impact.** Enforcement today is **human review only**. The `CLAUDE.md` rule
  is guidance with no detector behind it, unlike the adjacent log-prefix rules
  that checkstyle enforces mechanically (`BracketLabelInLog`, `CapsLabelInLog`,
  and siblings). A rule that depends on a reviewer noticing is caught
  inconsistently and recurs — exactly the pattern #831 exhibited inside a PR
  whose *subject* was QA hygiene. Because the cost (a dead reference, a brittle
  test) only surfaces after the referenced object is gone, the defect is cheap
  to introduce and expensive to find later, so it is well suited to a mechanical
  gate that fails the build the moment an ephemeral handle is introduced.
- **Proposal.** Add a mechanical check for ephemeral-identifier shapes — bare
  hexadecimal ids that look like tracker/job/run/workstream/memory handles,
  timestamped `*-YYYYMMDD-HHMMSS` branch/workstream names, and short commit SHAs
  — in source, test assertions, CI prompts (`tools/ci/prompts/`), and docs, with
  explicit exemptions for durable anchors (PR numbers `#NNN`, class and module
  names). A checkstyle rule can cover Java as the log-prefix rules do; a small
  CI lint can cover the non-Java prompts, tests, and docs. This is a proposal for
  a person to approve and for a separate branch to implement — not work for this
  docs round.
- **Current state (after the survey).** Partly acted on. Commit `dd3e9278f`,
  merged with PR #832, added `scripts/check-temporary-identifiers.py`. It runs
  as a step of the `checkstyle` job and is reported to auto-review as
  `temporary-identifiers`. The check reads its identifiers from the plan
  documents themselves (dated plan and retrospective names, the numbered items
  inside them, and `ledger.tsv` slugs) and fails when one appears in any other
  tracked file. The same commit also corrected the root `CLAUDE.md` rule. Under
  the corrected rule, a retrospective's item labels are temporary identifiers,
  not the durable anchors this proposal originally assumed, so any detector built
  for the remainder must not exempt them. What is still open is the part of the
  proposal the new check does not reach: the **generic** shapes (bare hex
  tracker/job/run/memory ids, short commit SHAs, timestamped branch and
  workstream names). Those are the shapes PR #831 actually leaked, and they are
  still caught by review alone.
- **Open question at the survey (since settled, see the end of this item).** A QA retrospective is itself a
  point-in-time evidentiary document and legitimately cites ephemeral handles as
  the evidence for its findings — this very report names job `c1cae26e`,
  workstream `project/task-20261031-170732`, and commit SHAs in its "single
  hardest-to-argue piece of evidence" list, because those *are* the evidence a
  future reader audits the finding against. Any mechanical check must therefore
  either exempt the retrospectives directory outright, or the retrospective
  format must be changed to prefer durable anchors (PR numbers, class/module
  names, dated finding labels) and cite ephemeral handles only where no durable
  anchor exists. Which of those two the project wants is a scope decision for the
  approver; it should be settled when `temp-id-enforcement` is scoped, not
  decided implicitly by the detector's glob. **Settled since the survey:** the
  root `CLAUDE.md` rule now classes `docs/qa/retrospectives/` (with
  `docs/plans/`) as disposable plan documents. `check-temporary-identifiers.py`
  does not scan those directories and instead reads identifiers from them. That
  is the first option above, the directory exemption, and a detector for the
  generic shapes should follow the same directory split.
- **Landing.** `ci/…` for the detector and checkstyle/CI-lint config (under the
  CI-file lock); person-only for the retrospective-exemption policy decision.

#### F4. Reusable QA rounds are now callable from downstream application repos, but the retrospective — the only backward-looking check — surveys only this repository (new)

- **Evidence.** One in-window `ci/` branch extracted the QA rounds into shared,
  reusable infrastructure and a second extended it for outside callers: PR
  **#785** (`ci/reusable-qa-rounds`, merged 2026-10-30) introduced
  `qa-round.yaml` as a reusable (`workflow_call`) workflow, which Master Agent
  Dispatch now calls for each of this repository's rounds and which another
  repository can call the same way; PR **#833**
  (`ci/qa-round-caller-workstreams`, merged 2026-11-03), titled "Give an
  **application's** QA round the framework checkout and a tracker role", did not
  extract anything further — it makes such a non-framework caller's round
  register with the framework cloned beside it (`DEPENDENT_REPOS`) and adds a
  `tracker-capabilities` input. The retrospective round,
  by contrast, is pinned to one repository by design — its prompt and this report
  survey `git@github.com:almostrealism/common.git` only, and must, because a job
  token can reach other repositories and those downstream repos are private.
- **Impact.** As application repositories begin running QA rounds through this
  shared infrastructure, their rounds' outcomes — did the PR merge, how many
  remediation cycles, where an agent looped — will be **invisible** to the one
  process that looks back at QA work. The feedback loop this round closes grows a
  blind spot exactly as the infrastructure it studies is generalised. There is a
  genuine tension to resolve, not just a feature to add: the retrospective's
  single-repo scope exists partly for privacy (no private workstream may be read
  or quoted), so cross-repo coverage cannot simply reuse this public report.
- **Proposal.** Decide the policy **before** application-repo rounds accumulate
  history: either give each consuming repository its own retrospective that
  writes into that repository, or have the shared infrastructure emit a
  per-repo, privacy-scoped QA summary that a human reads. No such history is
  visible in this survey — but that is not proof none has run: the reusable
  `qa-round.yaml` registers each caller's workstream under its own `REPO_URL`
  (`git@github.com:${{ github.repository }}.git`, the caller repo) and lists
  `common` only as `DEPENDENT_REPOS`, so an application round would not appear
  among the 524 all-`common` workstreams this repo-scoped survey counts. This is
  a person-level scope decision; the prompt change to record the decision is
