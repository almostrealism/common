## Findings by category

### Category 1 — the FlowTree agent harness

#### F1. The retrospective round produces no committed artifact (lead finding)

- **Evidence.** `qa/retro-20261016-225746`: job `f870cd96` (workstream `f78d57f2`)
  exited **SUCCESS at a cost of $25.52** (claude/opus), wrote its findings as
  memories and one progress message, and left **no commit, no branch on origin (404),
  and no pull request** (`github_pr_find` state=all → found:false).
  `qa/retro-20261018-013620`: branch exists on origin but is **0 commits ahead of
  master** (empty diffstat); its job timeline is empty; only an orientation memory
  remains. `git log --all -- 'docs/qa/retrospectives/RETRO-*.md'` returns **zero
  results in all of history**; the ledger has held only its header since it was
  created at setup (`a11843a3c`); `qa/retro` has **0 merges**.
- **Impact.** The round that is supposed to close the loop on every other round has,
  across two runs and >$25 of spend, delivered nothing a person can review. The
  harness commits the working tree, so a run that records its work only as memories
  and messages — never writing `docs/qa/retrospectives/RETRO-*.md` to disk — exits
  SUCCESS with nothing to commit. The retrospective prompt (`retrospective.txt`)
  reinforces this: it directs the agent to survey everything and *then* produce the
  report, with no instruction to write a skeleton artifact first, so a run that
  exhausts its budget or stalls during the (expensive) survey leaves no trace.
- **Proposal.** Make writing a skeleton `RETRO-<date>.md` plus the ledger row the
  **first** action in `retrospective.txt`, enriched incrementally, so any run that
  reaches the survey has already committed an artifact. Separately, the harness
  could treat a round whose contract is "produce a docs change" exiting with an empty
  working tree as DEGRADED rather than SUCCESS, so the non-delivery is visible.
- **Landing.** `ci/qa-…` branch (`tools/ci/prompts/retrospective.txt`); the
  status-classification half is harness Java under `flowtree/`. Possibly person-only:
  confirm the retro job's turn/budget allocation is sufficient for the survey it asks
  for.

#### F2. Harness git operations fail mid-round and mark jobs FAILED

- **Evidence.** On `qa/pdsl-20261013-060541` (PR #651): job `4c7c7e6c` FAILED with
  "Failed to sync with origin/qa/pdsl-20261013-060541 — both pull and reset failed",
  and the round's final job `94873308` FAILED with "Git commit failed after staging
  2 files". On `qa/coverage-20260930-034533` (PR #593): job `c6965059` FAILED with
  "Primary phase hard-failed (non-zero exit, 0s duration, no work performed)". All
  three rounds merged regardless.
- **Impact.** These are harness-layer git/execution failures, not agent-logic
  failures. They burn a job slot, mark a round FAILED (polluting the signal the
  retrospective and the stuck-job scanner rely on), and trigger retries. `PR #651`
  merged despite its *final* job being one of these FAILED git commits.
- **Proposal.** Harden the git sync/commit path (retry-with-backoff on a transient
  pull/reset race; distinguish "nothing to commit" from "commit failed") and classify
  a transient git failure distinctly from an agent failure. `feature/harness-loop-prevention`
  (PR #618) already reworked `GitCommitHandler`/`GitOperations` for the no-progress
  enforcement loop; this is adjacent, in the same files.
- **Landing.** Ordinary branch, harness Java under `flowtree/` (`GitCommitHandler`,
  `GitOperations`, `GitManagedJob`).

#### F3. QA workstreams registered then archived without ever running a job (observation)

- **Evidence.** 24 QA-prefixed workstreams for this repository have no job on record,
  including a whole 2026-10-18 01:36 sibling batch
  (`qa/defect-20261018-013620`, `qa/consolidate-20261018-013621`,
  `qa/docs-20261018-013622`, `qa/performance-20261018-013625`,
  `qa/retro-20261018-013620`) that was registered and archived with zero jobs, while
  siblings at other minutes the same day did run (`qa/coverage-20261018-013839` → PR
  #673; `qa/pdsl-20261018-011154` → PR #671).
- **Impact.** Either harmless cadence housekeeping (a round registered then skipped by
  the interval gate) or a real partial-dispatch failure. The two are
  indistinguishable from the data ar-manager exposes; disambiguating needs the
  controller's dispatch logs. Flagged, not asserted, to avoid a false finding.
- **Proposal.** A person should check the controller dispatch log for one of the
  jobless 01:36 workstreams; if it is housekeeping, suppress the workstream
  registration until the cadence gate says run; if it is a dropped dispatch, it is a
  reliability bug.
- **Landing.** Person-only (controller configuration / dispatch logs).

### Category 2 — the existing QA jobs

#### F4. The auto-review / auto-resolve loop has no per-PR convergence cap

- **Evidence.** PR #593 (`qa/coverage-20260930-034533`) was open **2026-09-30 →
  2026-10-17 (≈17.5 days)** and accumulated **93 commits** and **≥80 recorded jobs**
  (the timeline saturated the 80 I requested without reaching branch creation). The
  overwhelming majority of those jobs carry the description "No quality gate reported
  a finding on branch …" — the `general-review` fallback `auto-review` dispatches —
  interleaved with "## YOU BROKE THESE TESTS. YOU MUST FIX THEM." (`auto-resolve`),
  one "## THIS IS A JVM CRASH", one hard-fail, and one DEGRADED. Each remediation job
  committed and re-triggered CI, which dispatched the next `auto-review`. The loop
  ended only when a person merged; two job descriptions on #593/#651 are manual human
  dispatches ("this branch contains a lot of memory management…", "study the PR
  comment carefully").
- **Impact.** `auto-review` fires on attempt 1 of **every** CI run (per
  `.github/CLAUDE.md`), and every remediation commit is a new run, so a single PR can
  cycle indefinitely. A prior memory (`396187d0`) estimated this one workstream at
  ≈$799 over two weeks. This is the largest single cost sink found in the window, and
  it is distinct from the no-progress *enforcement* loop that PR #618 already fixed.
- **Proposal.** Add a per-PR remediation budget: after N consecutive `auto-review`
  rounds that produce only churn without a quality gate actually flipping
  red→green, stop auto-dispatching and ping a person instead of re-reviewing. The
  controller already has "newer work" skip logic to build on.
- **Landing.** `ci/qa-…` branch (`.github/workflows/` auto-review/auto-resolve submit
  wiring and `.github/CLAUDE.md`); the budget-tracking half may be controller
  configuration (person-only).

#### F5. The auto-review prompt has no scope boundary (escalation of prior proposal A)

- **Evidence.** A scope-guard audit of the round prompts: `coverage.txt`
  ("Stay inside `${TARGET}`… note it in your summary rather than fixing it here"),
  `consolidation.txt`, and `pdsl-migration.txt` each carry an explicit "stay in scope,
  defer the rest" instruction; `general-review.txt`, `defect-hunt.txt`,
  `performance.txt`, and `doc-qa.txt` carry **none**. `general-review.txt` — the prompt
  `auto-review` runs on a round's own branch — instead says "review the changes on
  this branch and **fix every issue you find**" and "Use `git diff
  origin/master...HEAD` to understand the full scope of changes". So a narrowly scoped
  round (e.g. coverage of one package) is handed to a reviewer told to fix *everything*
  on the branch, which pulls in production changes across modules — exactly how PR
  #593 reached 79 files across five modules from a single-package coverage target.
- **Impact.** The primary round stays scoped; `auto-review` is where scope leaks. The
  follow-up-task tool to defer out-of-scope work now exists (PR #653) but is not wired
  into `general-review.txt`.
- **Proposal.** Give `general-review.txt` the same "stay inside the round's declared
  target; route anything broader to a follow-up task" instruction `coverage.txt`
  already has, now that `tracker_file_follow_up_task` exists to receive it. This is a
  prompt edit mirroring an in-repo pattern — low effort, low risk — and it directly
  bounds F4's churn.
- **Landing.** `ci/qa-…` branch (`tools/ci/prompts/general-review.txt`, and the
  review-request builder if the target must be threaded through).

### Category 3 — new kinds of QA job

#### F6. A nondeterministic / flaky-test hunt round

- **Evidence.** Test determinism recurs as a problem the existing rounds only fix
  reactively: in-window commits `2f50cdb80` ("Make audio scene test renders
  deterministic"), `fae7b96d9` ("Fix the nondeterministic full-Jacobian weight
  gradient"), `c49f5f7a7` (hoisted kernel-index 64-bit fix for a gradient), and
  `feature/cuda-test-stability` (PR #625, the one DEGRADED non-QA round). The
  "## YOU BROKE THESE TESTS" `auto-resolve` churn visible throughout PR #593 and PR
  #651 is partly tests that fail nondeterministically under an agent's changes.
- **Impact.** No round proactively hunts flaky/nondeterministic tests; they are found
  only when they break a remediation cycle, which feeds F4's loop. The defect round
  hunts production bugs and the coverage round adds tests, but neither targets
  existing tests whose outcome is not a function of the code under test.
- **Proposal.** A `qa/flaky-…` round that repeatedly runs a bounded, rotating slice of
  the suite, flags tests whose pass/fail varies across runs on the same commit, and
  either fixes the determinism bug or files a follow-up task. Evidence here is lighter
  than for F1/F4/F5; propose it as a pilot on one module, not a full cadence job, until
  it proves its yield.
- **Landing.** `ci/qa-…` branch (new prompt `tools/ci/prompts/flaky-hunt.txt` plus
  cadence wiring in `master-agent-dispatch.yaml`). Creating a new Maven module is out
  of scope; this reuses the existing test runner.
