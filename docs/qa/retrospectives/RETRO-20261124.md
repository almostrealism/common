### Category 2 — the existing QA jobs

#### F2. QA rounds produced two owner-rejected "concealment" fixes for one `master` failure, each breaking a rule its own round prompt already stated; the live gaps are enforcement and two prompts (`defect-hunt`, `general-review`) that still omit the guard (new)

- **Evidence.** One `master` failure —
  `ChainedSubmissionTest#independentDispatchIsNotWedgedBehindALongRunningOne`, whose
  501-factor product renders a 500-level-deep expression that some macOS runners'
  clang rejects at its 256-bracket nesting limit (memory `5a931923`) — drew **three**
  attempts, two of them from QA rounds taking an approach the project's own rules
  forbid:
  1. PR **#1014** (`qa/flaky-20261120-221446`, a *flaky* round) changed
     `NAryExpression.getExpression` to drop brackets around a leading same-operator
     operand — a **render-time** change. It was **closed unmerged** (2026-11-21) and
     recorded by the next round as a rejected "concealment" attempt.
  2. PR **#1018** (`qa/master-fix-20261121-080216`, a *master-fix* round) added an
     `AR_HARDWARE_NATIVE_BRACKET_DEPTH` flag to **raise clang's limit**
     (`Clang.java`, `LlvmCommandProvider`, `NativeCompiler`). It merged only as an
     **off-by-default escape hatch**, not as the fix — again recorded as a rejected
     concealment attempt (memories `5a931923`, `e9192b6c`).
  3. The **correct** fix — merge nested `Product`/`Sum` at creation
     (`NAryExpression.mergeOperands`) — came from the owner's PR **#1028**
     `feature/merge-nested-expressions-at-creation` (merged 2026-11-22). The *next*
     `master-fix` round (`qa/master-fix-20261122-071110`) then correctly found #1028
     open, verified it fixed the test under the strict limit, and deferred rather than
     re-fixing — which is exactly the behaviour the first two rounds lacked.

  The root `CLAUDE.md` already states the rule both rounds broke: "Generated code is a
  symptom; fix the expression that produced it. Never change how the tree is rendered
  to a string, post-process the source, or raise a compiler limit… Redundant brackets,
  for example, mean two operations that should have been merged into one n-ary
  expression were not (`NAryExpression.mergeOperands`). Before fixing a failing test,
  read the open pull requests and their review comments for the same failure: an
  approach the owner has already rejected there is not available to you." But the two
  prompts the rounds actually ran under already carry that rule. `flaky-hunt.txt` (which
  #1014's flaky round ran) and `master-fix.txt` (which #1018's master-fix round ran) both
  `@include earlier-attempts.txt`, whose two sections state both halves. *"Find out what
  has already been tried, and what was refused"* requires the round to list the open pull
  requests, read their comments, and search tracker tasks and memories **before** changing
  code, and to treat an approach the owner rejected as off-limits. *"Fix the cause, not the
  place the failure surfaced"* names raising "the limit, the timeout or the tolerance" or
  changing "how a result is written out" as "worse than no fix," with deeply-nested
  generated source called out as an expression that "was built or simplified wrongly" whose
  fix "is in that expression… not in the compiler's settings." So #1014 and #1018 each broke
  a rule their own prompt already stated — a **compliance** failure, not a missing
  instruction. (`master-fix.txt`'s own step 3 guards only the test-side half — editing,
  weakening, skipping, widening a tolerance, inflating a timeout, raising `@TestDepth` — but
  the `@include` above it covers the renderer/compiler-limit class.) The genuine **prompt**
  gap is in the two prompts that do *not* include `earlier-attempts.txt`: `defect-hunt.txt`
  carries neither the open-PR check nor any concealment rule, and `general-review.txt` guards
  test-weakening (tolerance, `@TestDepth`, lost assertions) but has neither the "read the open
  PRs for the same failure first" step nor the generated-code renderer/compiler-limit
  concealment class. #1014 and #1018 each spent a round plus review passes (three on #1014) on
  an approach the owner then discarded.
- **Impact.** Wasted round, review and owner cycles on fixes that cannot land, and a
  worse outcome than waste: #1018's compiler-limit escape hatch *merged*. An
  off-by-default flag is harmless today, but the pattern — a QA round papering over a
  generated-code symptom at the renderer or the compiler — is exactly the class
  `CLAUDE.md` singles out as concealing the defect and forfeiting what the correct tree
  would have enabled. The second `master-fix` round shows the fix: checking open PRs
  for the same failure converts a duplicate attempt into a clean deferral.
- **Proposal.** Two distinct moves, because two of the four prompts already carry the rule
  and the other two do not. **(a) Close the prompt gap.** Give `defect-hunt.txt` and
  `general-review.txt` the guard that `flaky-hunt.txt` and `master-fix.txt` already get from
  `earlier-attempts.txt`: the cleanest form is to `@include earlier-attempts.txt` in
  `defect-hunt.txt` as the other two rounds do, and to add to `general-review.txt` both the
  "search open PRs and tracker tasks for the same failing `Class#method` first" step and an
  explicit instruction to flag as a defect any change that fixes a generated-code symptom at
  the renderer or by raising a compiler-limit / timeout / tolerance flag rather than in the
  `Expression` tree (`NAryExpression.mergeOperands` and the creation-time merges). Do **not**
  re-add these lines to `flaky-hunt.txt`/`master-fix.txt`, which already include them.
  **(b) Make the existing rule enforceable at review time, on every route.** Because #1014 and
  #1018 broke a rule their prompts already stated, the lever for those rounds is review-time
  enforcement rather than another instruction — but the enforcement has to reach the PR whatever
  auto-review route it takes. The `auto-review` `Select prompt` step picks exactly one prompt
  per PR (`build-failure` → `code-policy` → `quality-gates` → docs-only → `general-review`, first
  match), and only the last is built from `general-review.txt`; so a concealment check added only
  there reaches a PR only when it is not docs-only and the build, code-policy and quality gates
  all pass. A round whose PR trips one of those gates is reviewed under a different prompt and
  never sees the check. The route-independent home is the shared branch-feedback block
  `tools/ci/prompts/pr-feedback.txt`, which `append_branch_feedback` patches into *every* route's
  prompt (build-failure, code-policy, quality-gates, docs-review and general-review alike): a
  "flag as a defect any renderer/compiler-limit concealment of a generated-code symptom" check
  added there catches the #1014/#1018 pattern regardless of which route the round's PR took. The
  tracker-append capability #992 just added makes the "defer to the open PR" outcome concrete.
- **Landing.** `ci/qa-…` — `tools/ci/prompts/defect-hunt.txt` (the `@include`), the shared
  `tools/ci/prompts/pr-feedback.txt` (the route-independent concealment check), and
  `general-review.txt` (the general-review route's own "search open PRs first" step);
  `flaky-hunt.txt`/`master-fix.txt` already `@include earlier-attempts.txt` and are untouched.

#### F3. `#991` pinned the default test seed, which stabilizes CI but removes the signal the flaky round and its observed-flakes collector depend on; the built hunt mode (`AR_TEST_SEED=random`) is enabled nowhere (new)

- **Evidence.** `flaky-seed-default-source` (#991) did exactly what the prior run asked:
  `TestSuiteBase.resetRandomSeed()` now seeds the process-wide `DefaultRandomSource`
  with a fixed `DEFAULT_TEST_SEED` before **every** test method (when `AR_TEST_SEED` is
  unset), so a draw a test leaves to the default source is reproducible across runs.
  - **The reach is narrower than "every `TestSuiteBase` test," and the prior run's quantified
    example is outside it.** `#991` pins only the *default* source — draws that actually go
    through `DefaultRandomSource`. A test that constructs its own `new Random(seed)` and passes
    it to `org.almostrealism.collect.computations.Random` draws from that generator instead and
    is untouched. `DifferentialAttentionTest` and `DifferentialAttentionAssetTest` are of this
    second kind: each holds a `private final Random random = new Random(SEED)` and its `gaussian`
    helper draws from it, with a javadoc stating the `SEED` was added *because* the unseeded
    lambda draw occasionally reached a magnitude whose float32 rounding exceeded
    `lambdaReparameterization`'s absolute tolerance. So that GPU-FP32 flake — the one the prior
    run **quantified at 0.81%/run** — was already stabilized by the test's own seed before
    `#991`, and `#991` neither stabilized nor masked it. The finding below therefore names **no**
    confirmed currently-flaky test that draws from the default source; the size of the masked
    class is unquantified (see Open questions).
  - That is the intended CI-stability win, but it also removes the flaky round's signal
    for the **seed-dependent** flake subclass. The flaky round's leads come from
    `collect-observed-flakes.py`, which defines a flake as a test that "failed in one
    attempt… and passed in another," and from `rerun-flaky-tests.sh`, which re-runs the
    **same commit's** failed jobs. With the seed pinned, a seed-dependent test no longer
    flips between attempts: it either consistently passes (the flake is masked by a
    lucky seed — the underlying absolute-tolerance defect persists, dormant) or
    consistently fails (a hard failure caught by the PR gate or `master-fix`). Either
    way the observed-flakes collector and the round's own re-runs stop surfacing it.
  - The mechanism that recovers the hunt is already built and documented:
    `AR_TEST_SEED=random` makes `TestSuiteBase` choose a fresh, logged seed per test
    "to hunt order- or seed-dependent flakes," and a failing run replays with
    `-DAR_TEST_SEED=<seed>`. But a repo-wide search finds `AR_TEST_SEED` / `AR_RANDOM_SEED`
    set in **no** workflow or `tools/ci/` file — every run uses the fixed default seed.
    `TestSuiteBase` reads the setting through `SystemUtils.getProperty` (system property
    or environment variable), so the setting itself is one JVM property away — **but it
    has to reach the JVM that runs the tests**, which is not where the caller job's
    environment lands. The `flaky-qa` job in `master-agent-dispatch.yaml` does not run
    tests: it runs `submit-agent-job.sh`, which POSTs a fixed set of fields (prompt,
    branch, flags) to the controller and forwards **no** arbitrary environment variable
    to the agent. The agent then runs tests on a worker through the MCP test runner, in a
    separate process the caller job's env never touches; the `collect-observed-flakes.py`
    leads and `rerun-flaky-tests.sh` reruns read the separate **Build and Test**
    (`analysis.yaml`) runs, which are their own workflow runs again out of the caller
    job's reach. So `AR_TEST_SEED` reaches the tests only where the process that launches
    them sets it: the agent itself (instructed by `flaky-hunt.txt`) for its own
    reproduction runs, or the `analysis.yaml` test lanes for the collector's input. A
    caller-job env assignment reaches none of these (see Open questions).
- **Impact.** The class the macOS/Metal reach (`flaky-gpu-reach`, #893) was built to find —
  numerical flakes from an *unseeded default-source* fill feeding an absolute-tolerance
  assertion — is one `#991`'s default-seed pin can mask from the flaky round once such a
  test exists. The CI-stability win and the flaky-hunt capability are in tension for that
  class, and the project already shipped the knob (`AR_TEST_SEED=random`) that would resolve
  it; nothing turned it on. Two caveats bound how much this matters today, both from the
  evidence above: the finding names no confirmed test in that class (the quantified 0.81%/run
  example turned out to be independently seeded), and turning the knob on is not the
  one-line caller-job change it first looks like.
- **Proposal.** Keep seed-dependent flakes discoverable while ordinary CI keeps the stable
  default seed, by applying `AR_TEST_SEED=random` *where the tests actually run*, not on the
  caller job. Two distinct levers, because they feed two distinct signals:
  (a) **The agent's own reproduction.** Teach `flaky-hunt.txt` to run a suspect test under
  `AR_TEST_SEED=random`, record the logged per-test seed, and replay the failing seed with
  `-DAR_TEST_SEED=<seed>` as the deterministic reproduction. This is the agent setting the
  property on its own MCP test-runner invocations, so it works without any CI-workflow change.
  (b) **The observed-flakes input.** Restoring the `collect-observed-flakes.py` signal for
  this class needs `AR_TEST_SEED=random` on the `analysis.yaml` test lanes themselves (so
  retried Build-and-Test attempts can disagree), which is a larger, riskier change — it
  trades CI determinism for flake visibility on the very runs CI gates on — and may not be
  wanted at all. The underlying absolute-tolerance defect is still an owner fix (relative
  tolerance, or a seed in the passing region) — the win here is keeping the flake *observable*.
- **Landing.** Lever (a) is `ci/qa-…` — the `flaky-hunt.txt` instruction alone; it needs no
  env assignment on `flaky-qa`, which would not propagate. Lever (b), if wanted, is a
  separate `ci/…` change to the `analysis.yaml` test lanes and is out of scope for a prompt
  edit. See Open questions for why this is split.

## Open questions for the reviewer

These are the points a reviewer should weigh before accepting P2; a review pass
surfaced each against the code and they are recorded here rather than silently resolved,
so the decision stays with the person approving the proposal.

- **P2's motivating example does not demonstrate the masked class.** The 0.81%/run
  `DifferentialAttentionTest#lambdaReparameterization` flake is not an unseeded
  default-source flake: the test holds its own `new Random(SEED)` and draws every tensor
  from it (`gaussian`), and the `SEED` field's javadoc says it was added precisely to stop
  the unseeded lambda draw from exceeding the assertion's absolute tolerance. `#991` did
  not stabilize or mask it. The report consequently names **no** confirmed test that is
  flaky *and* draws from the default source, so the size — possibly zero today — of the
  class P2 protects is unquantified. A reviewer may reasonably ask for one confirmed
  example before spending even a prompt edit, or accept P2 as cheap insurance against a
  class that will appear as unseeded `rand`/`randn` tests are written.
- **The caller-job env lever in the original landing does not work.** Setting
  `AR_TEST_SEED` on the `flaky-qa` job (or the `qa-round.yaml` env it calls) does not reach
  any JVM that runs tests: that job runs `submit-agent-job.sh`, which forwards only a fixed
  set of fields to the controller and no arbitrary environment variable, and the agent runs
  its tests in a separate process on a worker. The viable agent-side lever is the
  `flaky-hunt.txt` instruction (the agent sets the property on its own MCP test-runner
  runs); the landing above has been corrected to that.
- **Restoring the observed-flakes collector's signal is a separate, larger change.**
  `collect-observed-flakes.py` derives leads from retried **Build and Test**
  (`analysis.yaml`) runs, which run at the pinned default seed; `rerun-flaky-tests.sh`
  reruns those same runs' failed jobs. A `flaky-hunt.txt` change therefore restores only
  the agent's own reproduction, not the collector's input. Making a seed-dependent test
  able to disagree between CI attempts would require `AR_TEST_SEED=random` on the
  `analysis.yaml` test lanes — which deliberately trades CI determinism for flake
  visibility on the runs CI gates on, a change whose desirability is itself an open
  question and well outside a prompt edit.
