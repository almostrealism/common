## Findings by category

### Category 1 — the FlowTree agent harness

#### F1. The Copilot review layer was dark for the entire window (new, lead finding)

- **Evidence.** Every Copilot review requested on an in-window PR returned the
  identical "Copilot was unable to review this pull request because the user who
  requested the review has reached their quota limit." PR #704 has **three** such
  reviews (ids `5596497782`, `5606330173`, `5606629308`; 2026-10-21) and PR #707
  has **two** (`5606622376`, `5606833726`; 2026-10-21). Prior-session memories
  record the same quota wall as far back as 2026-10-14 (memory `109059c0`:
  "Copilot hit quota on all three reviews").
- **Impact.** The PR review pipeline is designed around two automated reviewers:
  GitHub Copilot and the agent-driven `general-review` (`auto-review`). On every
  PR inspected, and in every prior-session memory that mentions Copilot since
  2026-10-14, Copilot posted only a quota notice and never a review — so for the
  window the agent `general-review` was the effective sole automated reviewer, and
  by F4 it re-reviews the same branch repeatedly while — until PR #704 lands the
  prior run's `review-scope-guard` — it still has no scope boundary. Nothing in the pipeline flags the absent layer: a quota notice
  is posted as a "review", so the PR looks reviewed.
- **Proposal.** Primarily person-only: set the organization as the billing source
  for Copilot code review (the quota message links the exact setting), or
  otherwise restore the Copilot quota. Separately, so the gap is visible rather
  than silent, the pipeline could detect a quota-limit review body and surface it
  (a one-line log / status note) instead of letting a no-op "review" stand in for
  a real one, and stop re-requesting a review it knows will be refused. The dark
  layer also has a direct cost in the pipeline: the `auto-review-submit` job in
  `analysis.yaml` submits with `DELAY_SECONDS: "300"` precisely so the agent
  "starts with" Copilot's review of the same push — a five-minute hold on every
  auto-review that, for this window, waited for a review that never came.
- **Landing.** Person-only (Copilot / org billing configuration). Nothing under
  `.github/workflows/` or `tools/ci/` requests a Copilot review; the agent-side
  request is `github_request_copilot_review` (or
  `github_create_pr(request_copilot_review=…)`) in the ar-manager MCP server (`tools/mcp/manager/github_tools.py`,
  `_request_copilot_review` in `server.py`), so detecting the quota notice there
  is an ordinary branch. If some requests instead come from a repository-level
  automatic Copilot review setting, that setting is person-only; this run did not
  establish which mechanism requested the reviews it saw. Shortening or dropping
  the `auto-review-submit` `DELAY_SECONDS` hold while Copilot is dark is a
  `ci/qa-…` branch.

#### F2. Transient harness git failures still surface as a round-level FAILED (carry-forward of P4, narrowed)

- **Evidence.** On `qa/pdsl-20261013-060541` (PR #651): job `94873308` FAILED with
  "Git commit failed after staging 2 files" and job `4c7c7e6c` FAILED with "both
  pull and reset failed" (raised by `GitRepositorySetup` when its `pull --ff-only`
  and the fallback `reset --hard origin/<branch>` both fail). Re-reading the code
  narrows the prior run's framing:
  `GitCommitHandler` already logs "No changes to commit" distinctly from "Git
  commit failed after staging N files", and already retries a non-fast-forward
  push (`GitPushReconciler`); commit `8c674240f` (2026-10-20) consolidated job git
  execution and fixed a dependent-repo identity bug. So the remaining gap is
  narrow — `GitRepositorySetup`'s fetch and pull/reset **sync** path throws on the
  first failure with no retry/backoff, which is what produced "both pull and reset
  failed", and a transient sync/commit failure is not classified apart from an
  agent-logic failure.
- **Impact.** A transient harness-layer git failure still marks a whole round
  FAILED with no marker that it was infrastructure rather than the agent,
  polluting the signal the retrospective and the stuck-job scanner read. No new
  occurrence appeared after 2026-10-19, so the evidence is unchanged from the
  prior run and the gap is narrower than first stated — hence ranked low, not
  dropped.
- **Proposal.** Add retry-with-backoff to the pull/reset sync path, and tag a
  transient harness git failure (sync race, lock contention) distinctly from an
  agent failure so a round is not marked FAILED for an infrastructure hiccup.
- **Landing.** Ordinary branch, harness Java under `flowtree/` (`GitRepositorySetup`
  for the sync retry; `GitCommitHandler`, `GitOperations`, `GitManagedJob` for the
  failure classification) — adjacent to the just-landed `8c674240f`.

### Category 2 — the existing QA jobs

#### F4. `auto-review` re-fires on every push with no per-PR convergence cap (carry-forward of P3, escalated)

- **Evidence.** `auto-review` dispatches on attempt 1 of every CI run, and every
  commit is a new run. Within the window, even trivially clean branches draw
  repeated no-op passes: PR #704 drew **three** (`24527bc9`, `55290767`,
  `27099dc0`), PR #707 **two**, PR #699 **two** — each described "No quality gate reported a finding". The pathological
  tail is unchanged from the prior run: PR #593 reached **≥80 jobs over ≈17.5
  days**. PR #704's new `enforceChanges` re-run cap bounds re-runs **inside a
  single job**; it does not bound the controller re-dispatching a fresh
  `auto-review` on each new CI run, which is the loop that produced #593.
- **Impact.** Per-round churn is low now (1–3 no-op passes), but it is structural
  and unbounded: the same mechanism that charges a few passes to a clean PR is the
  one that charged ≈$799 to PR #593. The just-landed single-job cap narrows the
  empty-result case but leaves the cross-run dispatch loop uncapped.
- **Proposal.** Add a per-PR remediation budget distinct from the single-job
  `enforceChanges` cap: after N consecutive `auto-review` rounds that produce only
  churn without a quality gate flipping red→green, stop auto-dispatching and ping a
  person. The controller already de-duplicates a submission when a job on the
  workstream started after the CI run (the `startedAfter` check in
  `FlowTreeApiEndpoint`), and commit `5ff6e7ff5` added controller-owned job-state
  tracking; those are the natural places to count consecutive no-finding passes.
- **Landing.** The counting and refusal are controller Java under `flowtree/runtime`
  (an ordinary branch); passing any per-PR context the controller needs from the
  `auto-review` submit step is a `ci/qa-…` branch. Choosing N is a person's call.

#### F5. The retrospective round never surveys open PRs or `ci/qa-…` branches for in-flight implementations of its own prior proposals (new)

- **Evidence.** PR #704 implements P1 and P2 but is **open, not merged**: on master,
  `retrospective.txt` is still survey-first and `general-review.txt` still says
  "fix every issue you find". A status check that read only master (git log)
  would have reported P1 and P2 as "still open" — and `github_pr_find` looks a PR
  up *by branch name*, so it cannot discover an implementing PR whose branch the
  agent does not already know. Either way the check could have triggered a person — or a future round — to re-request work already done.
  This run found #704 only because its branch name,
  `ci/qa-review-scope-and-retro-artifact`, happened to echo the proposal slugs;
  `retrospective.txt`'s "decide its current status from the evidence" step names
  no check for open or recently merged PRs, and its tool list omits
  `github_list_open_prs`, which job sessions are granted (it is in
  `McpConfigBuilder`'s ar-manager tool list) and which lists every open PR.
- **Impact.** The retrospective's core job — telling acted-on proposals from open
  ones — depends on catching in-flight implementations that have not yet merged.
  Without an explicit instruction, that catch rests on one agent noticing a branch
  name, and a miss produces a false "still open" that wastes a person's attention
  or causes duplicate implementation work. This directly degrades the signal the
  round exists to produce.
- **Proposal.** Add a step to `retrospective.txt`'s "Read your own history first"
  section: before classifying any prior proposal open, list open PRs with
  `github_list_open_prs` and in-window branches (including `ci/qa-…`) with
  `workstream_list`, check candidates with `github_pr_find(state="all")`, and
  classify a proposal "acted on — in flight" when a PR's title or commits name or
  implement it. Also add `github_list_open_prs` to the prompt's tool list. Low
  effort (a prompt edit), low risk, and it protects the correctness of every
  future run.
- **Landing.** `ci/qa-…` branch (`tools/ci/prompts/retrospective.txt`).

### Category 3 — new kinds of QA job

#### F6. A nondeterministic / flaky-test hunt round (carry-forward of P5, escalated)

- **Evidence.** Test determinism keeps surfacing as a problem the existing rounds
  only address reactively, and the window strengthened the case: PR #625
  (`feature/cuda-test-stability`) merged **DEGRADED** — the one DEGRADED non-QA
  round — and PR #677 (`feature/audio-render-test-determinism`) was **closed
  without merging** on 2026-10-19, a determinism fix that was attempted and
  abandoned. The "## YOU BROKE THESE TESTS" `auto-resolve` churn the prior run
  documented on PRs #593 and #651 is partly tests that fail nondeterministically
  under an agent's changes, which feeds F4's loop.
- **Impact.** No round proactively hunts flaky/nondeterministic tests; they are
  found only when they break a remediation cycle (feeding F4) or when a feature
  branch fights determinism and sometimes loses (#677). The defect round hunts
  production bugs and the coverage round adds tests, but neither targets existing
  tests whose outcome is not a function of the code under test.
- **Proposal.** A `qa/flaky-…` round that repeatedly runs a bounded, rotating
  slice of the suite on one fixed commit, flags tests whose pass/fail varies across
  runs, and either fixes the determinism bug or files a follow-up task. Start as a
  one-module pilot, not a full cadence job, until it proves its yield. Reuses the
  existing test runner; creating a new Maven module is out of scope.
- **Landing.** `ci/qa-…` branch (new prompt `tools/ci/prompts/flaky-hunt.txt` plus
  cadence wiring in `master-agent-dispatch.yaml`).
