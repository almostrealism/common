#### F2. The harness uses the raw task prompt as a fallback commit message, which becomes a PR's title when it is the first commit (new)

- **Evidence.** The one open QA round, **PR #914** (`qa/defect-20261114-063411`),
  is titled **"You are hunting for a real defect in this codebase and proving it
  exi…"** — the verbatim, truncated defect-hunt prompt. Its commit timeline shows
  the same fallback twice: `1817afd32` "You are hunting for a real defect in this
  codebase and proving it exi…" (the initial commit, from which the auto-created
  PR took its title) and `28a8143a` "please resolve issues highlighted by PR
  comments" (a review-resolve instruction committed verbatim). The round went on
  to find and fix a **real** defect — `9dc719a3` "Floor `IndexSequence.min()`
  exactly and saturate out-of-range bounds" — and has been in review since
  2026-11-14. By contrast, every other recent defect round carries a **descriptive**
  PR title derived from the work: #899 "Drain all queued analytics events in
  `StatsigEventDelivery.deliverAll`", #862 "Add test coverage for `ImageCanvas`
  PPM header dimensions", #851 "Stop `LocalResource` copies from dropping the
  first byte." So the prompt-as-title is an anomaly, not the norm — it occurs when
  a round's PR is auto-created from a prompt-worded first commit before a
  descriptive summary exists, and the title then never updates.
- **Impact.** An open PR that found a real bug sits in the reviewer's open-PR list
  for days under a title that says nothing about the bug, and two of its commits
  read as instructions rather than changes. The cost is reviewability and the
  audit trail, not correctness; but it is a concrete, checkable harness behavior
  with an obvious remedy.
- **Proposal.** Derive a round's PR title (and the fallback commit message) from
  the work rather than the prompt: require the round's `commit.txt`/descriptive
  commit before titling, or title the auto-created PR generically
  (`<round-name>: <branch>`) and refresh it from the final commit when the round
  completes. Never commit the raw prompt text as a message.
- **Landing.** An ordinary branch — the PR-creation and commit-message path is
  harness Java in `flowtree/runtime` (`CommitMessageBuilder` and the auto-create-PR
  step).

### Category 2 — the existing QA jobs

#### F3. The flaky round now reaches GPU flakes, but runs under the per-job test lock, so its test-side diagnoses cannot be landed by the round — they pool as open tracker tasks and get duplicated (new)

- **Evidence.** `flaky-gpu-reach` closed the *reach* gap (F2/P1 of the prior run):
  round `qa/flaky-20261115-142845` ran on a macOS/Metal host and, for the first
  time, **reproduced and quantified** a GPU-FP32 flake —
  `DifferentialAttentionTest#lambdaReparameterization`, 33 of 4096 seeded two-head
  trials (0.81%) exceeding the test's `1e-4` absolute tolerance, max error ~7 FP32
  ulp (memory `46fb2887`). It correctly diagnosed the defect as **test-side**:
  unseeded `randnFill()` plus a fixed absolute tolerance on unbounded-magnitude
  FP32 `exp(dot)` values. But it could **not** land the fix, and this is
  **by design**: the flaky round runs with `protect-test-files: "true"`
  (`master-agent-dispatch.yaml`, with the explicit comment "PROTECT_TEST_FILES
  stays on"), so the `@Test` body that holds the fill and the tolerance is locked
  to it. Two consequences follow, both on the record:
  1. **The round can only diagnose and hand off.** It filed follow-up task
     `30bf562c` ("Seed or relative-tolerance `DifferentialAttentionTest#lambda…`,
     flake quantified at ~0.8%/run on Metal FP32"). The fix for the *adjacent*
     test it named as its next target (`DifferentialAttentionAssetTest`, task
     `05abc9c4`) was ultimately landed not by any flaky round but by the owner's
     **PR #965** — and `05abc9c4` **closed 2026-11-17T21:48Z**, right after #965
     merged. The loop closes, but only when a non-locked unit (here, an owner
     feature branch) picks the diagnosis up.
  2. **Diagnoses pool, and duplicate.** `DifferentialAttentionTest#lambda…` already
     had an open task from a prior flaky round — `9564ddb4`, filed 2026-11-10 —
     but the macOS round could not append its quantified evidence to it (a
     non-planner agent can edit only tasks linked to its own workstream), so it
     filed a **second** task (`30bf562c`) for the **same** flake. Both are open.
     Alongside them, `fcaf8950`, `96f03d35`, `6c1067eb` and `8b5ef21f` are open
     flaky-characterization tasks with no owner, and `96f03d35` names a CUDA-only
     timeout that even a macOS/Metal host cannot reach.
  3. **The generic fix that would sidestep the lock is unimplemented.** Task
     `9a68c5cb` "Seedable default random source, reset per test" — the
     framework-level seed the prior proposal named as the *higher-leverage* route
     (a) — is **open, backlog**, filed by a person on 2026-10-23. #965 instead
     seeded two specific test files; the class (every unseeded-fill /
     absolute-tolerance test) is still fixed one test at a time.
- **Impact.** The reach fix worked, and the round is now doing exactly the right
  thing — reproduce, quantify, hand off. But because the fix for this flake class
  lives inside locked `@Test` bodies, the round can never close these itself; the
  diagnoses accumulate as tracker tasks that only a person or an owner branch
  works, and the round re-diagnoses and re-files (now duplicated) the same flake
  on the next cycle. This is distinct from `flaky-gpu-reach` (which was about the
  host) — it is about what happens *after* a successful reproduction under the
  test lock.
- **Proposal.** Two independent, low-risk levers, for a person to choose (do not
  weaken or lift the test lock — that is precisely the deception surface it
  guards):
  - **(primary) Implement the seedable default random source (open task
    `9a68c5cb`).** A framework-level seed makes the fills deterministic and
    replayable from **outside** the `@Test` body, so the per-job test lock is not
    in the way and the *flakiness* — the intermittent, host-dependent failure —
    is removed across the whole unseeded-fill class in one move rather than one
    test per owner PR. It does **not** by itself fix the absolute-tolerance defect:
    a seeded test can still fail, but now it fails *deterministically*, which turns
    an un-reproducible flake into a stable, diagnosable failure an owner can then
    correct (relative tolerance, or a seed in the passing region). Reproducibility
    is the leverage here, not an automatic pass. This is the prior proposal's route
    (a), still unbuilt, now with fresh evidence (a quantified, duplicated,
    still-open flake) that the per-test approach does not scale.
  - **(secondary) Make the flaky round deduplicate its hand-offs.** Before filing,
    have it search the tracker for an open task naming the same `Class#method` and
    append its evidence there instead of creating a new task (or grant the round's
    workstream permission to append to a matching follow-up).
- **Landing.** Primary: an ordinary branch — the random source is
  `PackedCollection.randnFill` in `compute/algebra`, with the shared default
  exposed through the test harness (`TestSuiteBase`/`TestFeatures`) in
  `engine/utils`. Secondary: `ci/qa-…` for the `flaky-hunt.txt` prompt change,
  plus possibly a small tracker-append capability (MCP tools, ordinary branch).
